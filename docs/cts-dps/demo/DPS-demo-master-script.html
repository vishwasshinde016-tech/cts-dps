CTS DPS demo: the master script

For the call with the Spring developers, the app (UI) developers and the architect · about 60 minutes · 20 Nov 2026, updated 23 Nov 2026 (observability and traceability, full setup)

The audience is seeing DPS for the first time, so the order is: show it working first, then explain how it works, then say what each team builds. Every phase says what to open, what to run, what to point at and what to say. The live flows use the architect's own documents (already downloaded in architect-documents\). Small DPS-made sample files are used only for the flows the architect's list has no document for: a waiver letter, a guarantee, an amended and restated agreement and a document set.

Phase 1. The problem DPS solves 2 min · everyone · no screen needed

SAY

"Today, when a bank signs a loan, someone reads the whole agreement, sometimes 300 pages, to find every covenant: the ratios the borrower must keep, the reports it must send and the things it must not do. Then they type them into the tracking system. It is slow, and things get missed.

DPS, the Document Processing Service, does that reading. It finds each covenant and gives it back with the page and the exact sentence it came from. A person still checks and approves every covenant. DPS never approves anything.

One sentence to remember: DPS reads and proposes. Spring decides. The DMS stores. Java calculates."

Phase 2. One simple picture 3 min · everyone · Archify

OPEN Browser tab 1: dps-complete.html. Stay on the top architecture view. Press Ctrl+plus so the room can read it.
SHOW

Point at the boxes from left to right, in this order: CTS UI → Spring app → DMS store → DPS (API, queue, worker) → back to Spring. Do not open the inner DPS blocks yet.

SAY

"Here is the whole journey.

  1. The RM uploads a document on the CTS screen.
  2. Spring stores it in the DMS. The stored file never changes.
  3. Spring sends DPS a job: 'read this document'. DPS answers straight away with a job number, and reads in the background.
  4. DPS sends back the covenants, each with its page and quote.
  5. Spring shows them to a person on the review screen. The person confirms or corrects them, and only then do they become real covenants in CTS.

Who owns what: the DMS stores, Spring approves and calculates, DPS reads and proposes, and the model runs in the bank's own Azure."

FOR YOU

Questions about workers, the queue or CrewAI go to phase 5: "I'll show the inside in ten minutes, right after the live run."

Appendix C. Questions you may get

QuestionAnswer
Does DPS ever approve or publish a covenant?No. Every result waits for a person in Spring. Even a clean agreement is stored as proposed.
What if the AI makes something up?Every value must quote the page it came from, and the quote is checked against the page text. A number not in its quote goes to review. The model cannot vouch for itself.
What if Azure is down?The job finishes on rules only, and the fields go to review. A model problem never fails a job.
How do you know nothing was missed?The ledger lists every duty sentence in the document and gives each an outcome. Anything not explained is a review item, and 10% of dismissals are sampled for a person.
Why does Spring send the approved covenants?People may have corrected DPS's first reading. An amendment or waiver must be compared with what was approved, not with what DPS once read.
Is the result format changing?Only additions: scope, conditions, baskets, equityCure, the waiver value and inForce. Code that ignores them keeps working.
Two companies with the same covenant?Two covenants, each with its own scope. If one clause binds both, it is flagged so a person can split it.
What does DPS store?Its own tables and the parsed pages. The file itself stays in the DMS. DPS never writes to the Spring database.
How fast is it?Spring gets the job ID in milliseconds. A 100-page native PDF is read in about a minute on rules; speed on the real VM with Azure is still to be measured.
Does it read scans?Yes. Pages without a text layer are read with local OCR (an English model, on our own machine); hard layouts and scanned tables go to the heavy pool, where Docling reads them. A scan of a few hundred pages takes minutes, not seconds, so it runs on the heavy pool.
Other currencies, such as LKR, AED or AUD?Yes, 44 currencies. A shared symbol such as 'Rs.' or '$' takes the currency the document itself names (Sri Lankan rupees, Australian dollars); if the document names none, the value gets no currency rather than a guess, and a person checks it.
How was it tested on real documents?On 72 real public documents from six countries, rules only and with the AI. Key statement figures (total assets, revenue, currency, unit) were checked against the PDFs; the 44 bugs found were fixed, each with a test. What is not proven yet: accuracy on the bank's own labelled documents.
Word and Excel?Yes. Word is read as logical pages, including form fields, footnotes and tracked changes; Excel flags hidden rows and missing saved values.
Can we see why the AI proposed a covenant?Yes. In DPS's history table each AI finding has the id of the AI read and the trace; dps_ai_call has the model, prompt version, tokens and time of each call with the same ids. Langfuse shows the same as a tree. The prompt and answer text are kept only if the bank switches it on (DPS_AI_TRACE_TEXT), masked.
Does tracing send our documents anywhere?No. Traces carry ids, counts and times, not document text. Langfuse runs on this machine, its own telemetry is off, and its ports are on 127.0.0.1.
Are we tied to Langfuse?No. DPS writes OpenTelemetry, the standard. In production the same traces can go to the bank's platform (Grafana Tempo, Azure Monitor, Dynatrace ...) by changing one address.
What if the tracing tool is down?Jobs carry on. Spans are sent in the background and dropped if nothing answers; the audit tables in DPS's database are written as always.

Appendix E. Words you will use
